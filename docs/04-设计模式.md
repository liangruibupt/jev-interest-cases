# 04 · 设计模式

TypeSafe 的核心心法：**代码掌控流程，Jev 只提供原子判断**。下面六个模式覆盖本项目全部场景。

## 1. Speculative fan-out（推测式扇出）— A2、B1、B4

把代码**可能**需要的所有问题一次发出，包括只在某些分支才用得上的（"如果是 bug，多严重？"）。并行评估几乎不加延迟，只多花几十个 tokens；代码按主分类结果只消费相关答案。**错误做法**是串行提问：先问类别、再按类别问细节——慢且贵。

## 2. Confidence-gated routing（置信度门控路由）— A2、B1、B4

答案告诉你"是什么"，confidence 告诉你"能不能行动"。高 → 自动；中 → 确认；低 → 人工。门限按动作风险分层（详见 02）。

## 3. Composite scoring（组合评分）— A2

把一个复杂判断拆成多个独立维度各问一个 Score，归一化后用代码里的权重相加。权重可见、可调、不必重跑推理；换岗位（IC vs 经理）只改系数。

## 4. Intent routing（意图路由）— B1

Jev 做最前面的分类器：意图 + 复杂度 + 危害信号一次请求，代码决定走确定性逻辑、便宜的 LLM、贵的 LLM 还是人工。昂贵资源只在真正需要时出场。

## 5. Cascade / verify（级联与验证）— B2、B3

便宜模型先做（生成、抽取、检索），Jev 逐项核验（引用是否支持结论、段落是否含注入、字段是否被捏造），只有触发信号才升级到贵模型或人工。核验成本约为生成的 0.3%。

## 6. Select, don't generate（选而不写）— B4、A3

需要"抽取"时，先用正则/代码找出候选，再让 Jev 从候选中选；数字、日期留给代码解析。Jev 只判断"有没有提到数字"，不判断"数字是多少"。

## 何时需要第二次请求

只有当第二批问题依赖第一批答案来**构造新 state 或新选项**时：B4 把复合指令拆成多条再逐条问；官方 cookbook 里的层级分类按上一层结果决定下一层选项。其余情况都应一次问完。
