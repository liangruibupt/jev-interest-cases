# 03 · 与 LLM 的差异与局限

## Jev 的优势（相对 LLM）

| 维度 | 官方/实测依据 |
|---|---|
| 速度 | 约 100–150ms；8 题审核请求 114ms，Claude Haiku 4.5 同题 3.85s，Opus 4.8 推理模式 10.4s |
| 价格 | $0.042/Mtok 输入、输出免费；同一 8 题请求 $0.000046 vs Haiku $0.0035（76×）vs Opus 4.8 推理 $0.028（617×） |
| 并行 | 一次请求多题并行；13 题打包 vs 单发：12.2× 便宜、10× 快 |
| 校准 | RLCD 直接优化概率校准；LLM 的概率是"说出来的" |
| 一致性 | 15 轮重复的标签一致率 90.8%，概率标准差均值 0.0098（LLM 默认采样 0.03–0.05） |
| 类型安全 | 输出被约束在你给的选项/等级内，代码无需解析文本 |

## Jev 的短板（jev-1.13 官方 jaggedness 清单）

| # | 短板 | 该怎么做 |
|---|---|---|
| 1 | **字面理解**：按你写的字答，不揣测意图；否定、限定词按字面读 | 把条件写全；把"我本来想问的"补进 instructions；必要时拆成两个字面问题 |
| 2 | **算数与计数**：不可靠 | 在代码里算；要"数满足条件的项"就每项一个 Noul，代码求和 |
| 3 | **日期比较**：把日期当文本 | 用 Choice 抽取年/月/日各部分，代码组装比较 |
| 4 | **多跳间接**：双重否定、"属性的属性"不稳 | 直接问；用反引号指向具体字段 |
| 5 | **无关上下文越多越差**（context rot） | 先在代码里过滤，只发问题需要的字段 |
| 6 | **对抗内容**：state 里的诱导性文字会影响答案 | criteria 写明确；上线前用边界样本测试；护栏不是安全边界 |
| 7 | **instructions 与 criteria 矛盾**会混乱 | 让 criteria 成为 instructions 的延伸；不要 true 表示"否" |
| 8 | **无结构不变量**：Noul ≠ 二选一 Choice；P(A)+P(非A) ≠ 1 | 每个判断只用一种问法；阈值不跨问法迁移 |
| 9 | **不做生成**：不会写文字、代码 | 交给 Claude；抽取时让 Jev 从候选中"选"而不是"写" |

另外：**英文为主**。中文输入可用但准确率与置信度都会下降（A1 的预置 7 可直观对比）。

## 一致性 ≠ 确定性

Jev 不是确定性的：官方 15 轮实验里 8 题有 2 题的最高标签会翻转（两选项概率接近时）。这不是缺陷而是诚实——用 `probability < 0.6 → uncertain → 人工` 的规则可把策略级一致率提到 99.2%。相反，LLM 设 temperature=0 能得到近零方差，但那只是"每次说同样的话"，不代表校准。
