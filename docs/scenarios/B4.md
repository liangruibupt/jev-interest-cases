# B4 · 自然语言智能家居助手（带概率的 function calling）

**目标**：一句英文指令 → **一次 Jev 请求、14 个 speculative 问题** → 代码按门限分派成命令，直接驱动房屋。这就是"每个参数都带概率的 function calling"：类别、房间、设备、动作、亮度、颜色各有自己的分布与置信度，代码决定用哪些、忽略哪些。数字交给正则；开锁必须确认；Claude 只在**拆分复合指令**和**闲聊 / 状态问答**时出场。

页面：`/b4`。代码：`shared/src/scenarios/b4-smart-home/{home,examples,questions,thresholds,numbers,dispatch}.ts`、`server/src/routes/b4.ts`（`POST /api/b4/command`）、`web/src/components/FloorPlan.tsx`、`web/src/pages/B4SmartHome.tsx`。

## 房屋与命令

5 个房间（客厅 / 厨房 / 卧室 / 浴室 / 书房），每间有灯（开关、亮度 off/dim/medium/bright、颜色）、温控、窗帘、音箱、电视；房屋级前门锁。`applyCommand(home, cmd)` 是纯 reducer，浏览器持有状态并在 SVG 平面图上渲染。

## 发给 Jev 的东西

**state**：`{ request, rooms: [5 个房间 id], devices: [6 个设备 id] }`。

| id | 类型 | 英文原文（节选） | 用途 |
|---|---|---|---|
| category | Choice | What kind of request is `request`? · device_command / information_question / chit_chat / other | 第一道分流 |
| is_compound | Noul | Does `request` ask for more than one distinct action…? · false "A single action, even if it applies to several rooms at once" | ≥ 0.7 → Claude 拆分 |
| room | Choice | Which room does `request` refer to? · 5 房间 + whole_house + not_stated | 目标房间 |
| device | Choice | Which device does `request` want to control or ask about? · 6 设备 + not_stated | 目标设备 |
| light_action / thermostat_action / blinds_action / speaker_action / tv_action / lock_action | Choice（speculative） | If `request` is about X, what should happen? · 各自的动作 + not_applicable | 只用命中设备那一个 |
| brightness_level / color | Choice（speculative） | If `request` sets a brightness level in words / names a light color… · + not_stated | 灯的参数 |
| mentions_number | Noul | Does `request` contain a specific number for a temperature, percentage, or volume level? | 提示代码去正则 |
| is_question_about_state | Noul | Is `request` asking what the current state of something is, rather than asking to change it? | 状态询问 |

**门限**（`thresholds.ts`）：category 0.5 · compound 0.7 · room 0.5 · device 0.6 · action 0.5 · **lock 0.85** · stateQuestion 0.7。

**分派**（`dispatch.ts`，顺序首中）：category 置信度不足或 other → 追问 · chit_chat → Claude 闲聊 · information_question 或 is_question_about_state ≥ 0.7 → Claude 读房屋状态回答 · is_compound ≥ 0.7 → Claude 拆分后每段再问 Jev · 设备 / 房间缺失或置信度不足 → 追问 · 门锁：unlock 永远确认，lock 置信度 < 0.85 确认 · 其余按设备的动作 Choice 生成命令；数字只来自 `numbers.ts` 的正则（21 degrees / 30% / volume to 4），百分比优先于"dim/medium/bright"文字。

- **20/20** 与预期一致；20 次请求 28,443 tokens（每条约 1,420）、**$0.0012**，p50 580 ms、最慢 1.19 s。
- 设备类判断几乎全是 1.00：对结构清晰的指令，14 个问题一次请求就够了；被忽略的 speculative 答案（其它设备的动作）在轨迹里可展开查看。
- 两条"缺房间"的指令都被正确追问；"make it brighter" 里 Jev 其实很确定是灯（0.99），只是房间 not_stated（0.55）。
- "turn everything off in the living room" 落在门限边上：is_compound 0.64（< 0.7）、device not_stated 0.45——它既不是单一设备也没被判为复合，于是追问。把 compound 门限调到 0.6 它会走拆分；这是产品决策。
- 三条复合指令 is_compound 0.92–0.99，与单一指令（≤ 0.12）分得很开。

## 实测二：页面上的四步（Sonnet 5 参与两步）

| 指令 | 结果 | Jev | Claude |
|---|---|---|---|
| turn off all the lights | 全屋灯 → 关闭（whole_house 0.98） | 1 次，$0.00006 | — |
| turn off the kitchen lights and close the bedroom blinds | 拆分为 2 条 → 厨房灯关；卧室窗帘关 | 1 + 2 次 | 拆分 4.6 s，$0.0020 |
| unlock the front door | 弹出确认（置信度 1.00 仍要确认）→ 确认后开锁 | 1 次（确认时缓存命中） | — |
| is the front door locked? | "No, the front door is not locked." | 1 次 | 4.1 s，$0.0012 |

首次点复合指令时 Bedrock 一次响应超过 60 s，被 Vite 开发代理以 504 切断；服务端直连复现只需 8.2 s。已把开发代理超时改为 180 s，并给 API 加了请求日志。

## 成本对比

| 层面 | Jev | LLM 基线 | 下降 |
|---|---|---|---|
| 纯设备指令（每条） | $0.00006（≈1,420 tokens） | Sonnet 5 function calling ≈ $0.0040 | **98.5%（68×）** |
| 20 条混合流量 | Jev $0.0012 + Claude（4 次拆分 ≈ $0.008、2 次闲聊 + 2 次状态 ≈ $0.005）≈ **$0.014** | 全部走 Sonnet 5 function calling ≈ $0.081 | **≈ 83%（6×）** |
| 延迟 | 0.4–1.2 s | 4–5 s（本网络） | 单一指令快 4–8 倍 |

## 试一试

1. 先发 "lock the front door"（直接执行），再发 "unlock the front door"（必须确认）：同样 1.00 的置信度，风险决定门限。
2. 发一条复合指令，展开"Claude 拆分出的子指令"看每段各自命中的规则——这是文档允许的第二次 Jev 请求（新 state）。
3. 把 "turn the TV off" 改成 "turn the living room TV off"，追问消失。
4. 发 "set the bedroom to twenty degrees"：正则取不到数字，看 mentions_number 与追问"设到几度？"。

## 陷阱

- 数字永远在代码里解析；Jev 只回答"有没有数字"。
- 拆分质量取决于 Claude；拆错时每段仍被 Jev 独立判断，但意图可能已丢失。
- 同一设备的两个参数（"warm white and dim"）会被判为复合（0.92）：拆开执行结果一样，只是多一次 Claude。
- 门锁这类不可逆动作永远保留人工确认；0.85 只是"直接上锁"的门限。
