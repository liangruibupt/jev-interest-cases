# B1 · 护栏 + 模型路由（Jev 在 Claude 前）

**目标**：把 Jev 放在 LLM 前面当"分流器 + 护栏"：每条用户消息先经 Jev 一次请求（10 个问题），代码按策略决定走固定回复、拦截、转人工、FAQ 直答，还是 Claude Sonnet 5 / Opus 5。Claude 只在真正需要生成时出场——这就是官方所说的 Harness Engineering 用法。

页面：`/b1`。代码：`shared/src/datasets/guardrailMessages.ts`（16 条消息 + 人工标注）、`shared/src/scenarios/b1-router/{questions,thresholds,policy,faq,state}.ts`、`server/src/routes/b1.ts`（`POST /api/b1/message`）、`web/src/pages/B1Router.tsx`、`web/src/components/DecisionTrace.tsx`。

## 发给 Jev 的东西

**state**：`{ message, recent_context: [最近两条用户消息] }`。

**10 个问题（一次请求）**：

| id | 类型 | 英文原文（节选） | 用途 |
|---|---|---|---|
| intent | Choice | What is the user primarily asking for in `message`? · faq / account_action / product_question / technical_help / complaint / chit_chat / other（结构化 `what / not_for`） | 路由主依据 |
| faq_topic | Choice（speculative） | If `message` asks a standard policy question, which topic is it? · 8 个话题 + none | FAQ 直答查表 |
| complexity | Score | How much work is needed to answer `message` well? · 一行事实 / 需要推理或多步 / 深度推理、带代码调试或异常情况 | Sonnet 还是 Opus |
| jailbreak | Noul | …try to get the assistant to ignore, override, or reveal its instructions, or to role-play as an AI with no rules? | 护栏 |
| harmful_request | Noul | …ask for help causing physical harm to people, or for help breaking the law? | 护栏 |
| medical_advice | Noul | …ask for a diagnosis, a specific drug dosage, or a treatment decision…? | 谨慎路由 |
| self_harm | Noul | …suggest the person sending it may be considering harming themselves? | 固定支持回复 |
| severity | Score | How much harm could result if the assistant complied? · No harm / Mild / Serious / Severe | 护栏加权 |
| wants_human | Noul | …explicitly ask to speak with a human agent or a manager? | 转人工 |
| is_compound | Noul | …contain more than one unrelated request? | 展示用（B4 会真正用它） |

危害类问题的措辞沿用官方 guardrails cookbook。

## 策略（`policy.ts`，顺序首中）

| # | 规则 | 路由 |
|---|---|---|
| 1 | self_harm ≥ act | 固定支持回复（不调 LLM） |
| 2 | jailbreak 或 harmful_request ≥ act | 拦截 |
| 3 | severity ≥ 2.0 且任一危害 ≥ review(0.35) | 拦截 |
| 4 | wants_human ≥ 0.8 | 转人工 |
| 5 | intent 置信度 < 0.5 | 转人工（意图不明不硬猜） |
| 6 | medical_advice ≥ act | Sonnet 5 + 医疗谨慎 system 提示 |
| 7 | intent = faq 且 complexity ≤ 0.7 且 faq_topic ≠ none 且其置信度 ≥ 0.6 | FAQ 直答（查表，零模型） |
| 8 | intent = complaint 且 complexity ≥ 1.0 | 转人工 |
| 9 | complexity ≥ opusMinComplexity | Claude Opus 5 |
| 10 | 其余 | Claude Sonnet 5 |

两套预设：**严格** act = 0.70，**宽松** act = 0.85；页面切换时对已有轮次在浏览器里重算，标出"按当前策略会走 → …"。

### 一次基于数据的调参

设计稿把 Opus 门限定为 complexity ≥ 1.5。实测 M07（带代码的 webhook 签名调试）两次得到 1.36 和 1.48：Jev 的分布是 6% / 39% / 55%，"深度调试"已占多数，却因为期望值不到 1.5 被送去 Sonnet 5（回答也对：应对原始请求体计算 HMAC）。我们把 `opusMinComplexity` 调到 **1.3**：让"过半概率是深度问题"的消息走 Opus，而 M09（0.89）、M11（0.88）等仍留在 Sonnet。这正是 Score 的用法——看分布而不是只看一个数字，然后把门限写进代码。

- 命中 **16/16**；宽松策略下路由完全相同（本组没有落在 0.70–0.85 之间的危害信号）。
- 危害信号非常干净：13 条普通消息的四个危害 Noul 全部 ≤ 0.03；三条问题消息各自的信号 ≥ 0.93。
- 有趣的是 M12（剂量询问）与 M13/M14 的 intent 都是 `other`：这类消息本来就不属于客服意图分类，intent 置信度仍很高——说明 `other` 选项的重要性。
- 16 次请求 17,940 tokens（每条约 1,120），$0.00075，延迟 p50 543ms、最大 1.06s。

## 成本对比

| 层面 | Jev | LLM 基线 | 下降 |
|---|---|---|---|
| 分类 / 护栏步骤（16 条） | $0.00075 | Sonnet 5 做同样分类 $0.068 | **98.9%（90×）** |
| 端到端（页面 3 条） | $0.0030 | 全走 Opus 5 $0.0232 | **87%** |
| 零 LLM 路由占比（16 条） | FAQ 4 + 拦截 1 + 支持 1 + 人工 2 = **8/16** | — | 一半的消息根本不需要生成 |

## 试一试

1. 切到"宽松"，再发 M13：act 升到 0.85，越狱 0.99 仍被拦；把 M13 改写得更含蓄，看信号如何下降。
2. 自己写一条混合消息（"How do I reset my password, and also why was I charged twice?"），看 `is_compound` 与路由。
3. 发一条中文消息，比较各信号的置信度。
4. 把 `B1_POLICIES.strict.opusMinComplexity` 改回 1.5 或降到 1.0，观察 M07 / M09 / M11 的去向。

## 陷阱

- 护栏不是安全边界：官方明确 Jev 对对抗性内容并不免疫，上线前用边界样本测试。
- 阈值随风险变化：拦截 0.70、要真人 0.80、意图 0.50、Opus 1.3 都只是起点。
- 靠近门限的消息在两次运行中可能走不同路由（见 A4 的漂移数据）；把这类消息送人工是合理的策略。
- 转人工与 FAQ 直答的"零成本"不包括人的时间。
