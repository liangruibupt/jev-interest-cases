# C4 · VPP 调度通知与告警（能源）

**目标**：把"能源判断"里 Jev 能做的那一层拆出来：**这份通知是否适用于本站点、要不要做事、是不是测试、告警属于哪类**。12 条来自电网调度机构、聚合商、遥测系统与客户的通知，对 3 个虚拟电厂（VPP）站点逐对判断：每对（通知 × 站点）一次 Jev 请求、9 个问题。kW / MW 容量门槛、限出力百分比、时间窗、截止时间由代码解析并与站点档案比较，Jev 只判断词。代码把每对路由到**立即行动 / 排期 / 仅告知 / 测试确认 / 告警 / 不适用 / 复核**。没有问"现在该不该放电""报什么价"。

页面：`/c4`。代码：`shared/src/datasets/vppNotices.ts`（3 个站点、12 条通知，虚构）、`shared/src/scenarios/c4-vpp/{questions,thresholds,constraints,compose}.ts`、`server/src/routes/c4.ts`（`POST /api/c4/apply`）、`web/src/pages/C4Vpp.tsx`。纯 Jev。

## 站点

| id | 名称 | 区域 | 资产 | 容量 |
|---|---|---|---|---|
| S1 | Harbor Point BESS | North Zone | 电池储能 | 2,000 kW |
| S2 | Sunfield Solar+Storage | South Zone | 光储 | 800 kW |

## 发给 Jev 的东西

**state**：`{ notice, from, site: { name, region, asset_type } }`——容量不在 state 里，Jev 不需要也不该比较它。

| id | 类型 | 英文原文（节选） | 用途 |
|---|---|---|---|
| notice_type | Choice（11 类） | What kind of message is `notice`? · dispatch_instruction / demand_response_event / curtailment / test_event / market_information / maintenance / settlement / alarm / customer_request / registration / other | 分类；alarm / customer_request 走"点名"逻辑 |
| applies_region | Noul | Does `notice` apply to sites located in `site.region`? · true "names that zone, or does not limit itself to any particular zone" · false "limits itself to other zones only" | 适用性 |
| applies_asset | Noul | Does `notice` apply to resources of the kind in `site.asset_type`? · true "…or does not limit itself to particular kinds of resource" · false "…or explicitly excludes this kind" | 适用性 |
| names_site | Noul | Does `notice` refer to `site.name` specifically…? | 点名类通知的唯一依据 |
| addressed_to_one_site | Noul | Is `notice` addressed to one specific named site or asset, rather than to a zone or a class of resources? | 点名别的站点的通知不泄漏到同区同类邻居 |
| requires_action | Noul | …require the operator of the site to do something (dispatch, curtail, respond, confirm, re-register, exclude), rather than only informing them? | 行动 vs 告知 |
| is_test | Noul | Is `notice` a test or drill with no real response required? | 测试确认 |
| urgency | Score（3 级） | How soon does `notice` need attention…? · 仅告知 / 几天内 / 现在或数小时内 | 立即行动 vs 排期 |
| alarm_category | Choice | If `notice` is an alarm…what kind? · telemetry / communications / hardware / safety / market / not_an_alarm | 告警队列 |

**代码解析的约束**（`constraints.ts`）：容量门槛（"at least 1 MW" → 1,000 kW，与站点容量比较）、限出力百分比（"curtail output to 50%"）、时间窗（"16:00 to 19:00"）、截止时间（"by 12:00 tomorrow"）。

## 规则（`compose.ts`，顺序首中）

| # | 规则 | 路由 |
|---|---|---|
| 1 | 代码比较：容量门槛不满足，且通知不是点名类、也没点名本站点 | 不适用 |
| 1b | addressed_to_one_site ≥ 0.7 且 names_site < 0.35：通知点名的是别的站点 | 不适用 |
| 2 | 点名类通知（notice_type 为 alarm / customer_request，或 alarm_category 非 not_an_alarm 且置信度 ≥ 0.7）：names_site ≥ 0.5 → 适用；0.35–0.5 → 复核；< 0.35 → 不适用（区域词、资产词、容量门槛对它们不起作用） | — |
| 3 | 其它通知：names_site ≥ 0.7 直接适用；否则 applies_region 与 applies_asset 都 ≥ 0.7 才适用，任一 < 0.35 不适用，其余复核 | — |
| 4 | is_test ≥ 0.7 | 测试 · 确认收到 |
| 5 | 告警类别 ≠ not_an_alarm 且置信度 ≥ 0.7，或类型为 alarm | 告警 |
| 6 | requires_action ≥ 0.7：urgency ≥ 1.5 → 立即行动，否则 → 排期 | — |
| 7 | 其余 | 仅告知 |

### 两次基于数据的修正

第一次关缓存运行只有 26/36：
- 门户维护、结算、注册提醒这类**不提区域**的通知，Jev 对"是否适用于该区域"只给 0.4–0.6，全部落进复核。原来的 true 描述写的是"names that zone, or says all zones"，而这些通知谁都没说。改成"does not limit itself to any particular zone"后，N11 三个站点的 applies_region 从 0.45 / 0.46 / 0.38 升到 0.88 / 0.86 / 0.86。**问法决定答案。**
- 遥测告警与客户请求本来就只关乎一个站点，"Riverside Commercial gateway" 对站点 "Riverside Commercial DR" 的 names_site 是 0.58–0.67，差一点到 0.7；而区域 / 资产词对这类通知没有意义。于是给点名类通知单独一条规则：只看 names_site，门限 0.5。
- N01（北区需求响应事件）对电池站点 S1：通知写的是 "enrolled demand response loads"，Jev 给 applies_asset 0.86——它按字面把注册了的北区电池也当作可参与资源。电池能否算 DR 负荷取决于注册情况，标注放宽为接受两种结果。

修正后两次运行都是 **36/36**。
- 审查时发现的第三个问题：一条点名 "Harbor Point BESS" 的调度指令，对同区同类型的另一个电池站点会因为区域词、资产词都匹配而被判为适用。三个演示站点资产类型互不相同，所以 36 对里没暴露；加了第 9 个问题 `addressed_to_one_site`，点名别的站点的通知直接不适用。

- **36/36** 路由落在人工标注；通知类型 36 对全部一致（同一通知对三个站点判为同一类）。
- **数字在代码里**：N02 对 S2 / S3 的"不适用"不是 Jev 说的——Jev 对三个站点的 applies_asset 都 ≥ 0.79，是代码把 800 kW、350 kW 与 1 MW 比出来的。
- **N12 是"明确排除"的示范**：通知写了 "Battery and solar resources … need not act"，S1 / S2 的 applies_asset 直接掉到 0.20 / 0.22。
- N06 的 names_site 只有 0.6 左右：站点名叫 "Riverside Commercial DR"，通知说 "Riverside Commercial gateway"；点名类通知门限 0.5 接住了它，0.35–0.5 之间则交复核。
- 36 次请求 40,716 tokens（每对约 1,130）、**$0.00171**；缓存回放这一轮 p50 0.69 s、最慢 3.36 s（关缓存冒烟：p50 约 0.7 s，偶有 5 s 离群）。

## 试一试

1. 看 N02 三格：同一条测试通知，S1 测试确认、S2 / S3 不适用，差别全在代码的容量比较。
2. 把"适用 / 行动 Noul ≥"拉到 0.9：N07 的 requires_action 在 0.7–0.8，掉出后三格从排期变成仅告知。
3. 把 N01 的 "demand response loads" 改成 "demand response loads (batteries are not eligible)"，看 S1 的 applies_asset 如何变化。
4. 改 `parseConstraints` 让 "one megawatt" 也能解析：正则是代码，随文本演进。

## 陷阱

- Jev 不做调度决策：放电与否、报价多少属于优化与合约。
- 真实调度通知多有固定格式：先按格式提取字段（代码），再让 Jev 判断自然语言部分。
- 站点名匹配靠字面：通知里的别名、缩写要么写进站点档案，要么接受复核。
- 门限附近会漂移：N06、N10 的 names_site 都在 0.55–0.65，离 0.5 不远；几次运行里稳定，但真实系统要留复核队列。
