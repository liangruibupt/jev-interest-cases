# A2 · 工单分流看板

**目标**：用一个真实业务形态（客服工单分流）体会三件事：**speculative fan-out**（每条工单一次请求、10 个问题并行，代码只消费相关分支）、**confidence-gated routing**（置信度不足或垃圾风险落在灰区就交给人）、**判断即数据**（阈值与权重是代码常量，拖滑杆重排不产生任何推理）。

页面：`/a2`。代码：`shared/src/datasets/tickets.ts`（24 条英文工单 + 人工标注的可接受泳道）、`shared/src/scenarios/a2-triage/{questions,thresholds,compose,state}.ts`、`server/src/routes/a2.ts`（`POST /api/a2/evaluate`，服务端扇出、并发 6）、`web/src/pages/A2Triage.tsx`。

## 发给 Jev 的东西

**state**（每条工单）：只包含问题需要的字段，绝不包含人工标签。

```json
{ "ticket": { "subject", "message", "sender": { "display_name", "email" }, "links": [] },
  "customer": { "plan", "open_orders": [{ "id", "status" }] },
  "policy": { "sensitive_credentials": ["password", "security code", "API key", "one-time code"] } }
```

**10 个问题（一次请求）**：

| id | 类型 | 英文原文（节选） | 中文释义 | 何时被代码使用 |
|---|---|---|---|---|
| department | Choice | Which team should handle `ticket.message`? · billing/orders/account/technical 各带 `{what, not_for, examples}` · other | 主责部门 | 总是 |
| requested_resolution | Choice | What does the customer want to happen? refund / exchange / replacement / fix / information / other | 客户想要的结果 | 账单、订单泳道 |
| bug_severity | Score | If `ticket.message` reports a defect or outage, how severe is it? 3 级情境 | 缺陷严重度 | 技术泳道 |
| has_repro_steps | Noul | …describe specific steps to reproduce a problem, or name the environment? | 有复现步骤/环境 | 技术泳道 |
| refund_requested | Noul | …explicitly ask for money back or an account credit? | 明确要退款 | 账单、订单、复核 |
| requests_credentials | Noul | …ask the recipient to disclose a credential listed in `policy.sensitive_credentials`? focus: 索要凭证本身，不是重置指引 | 索要凭证 | 总是（垃圾风险） |
| sender_identity_mismatch | Noul | Does the organization in `ticket.sender.display_name` conflict with the domain of `ticket.sender.email`? | 发件人身份不符 | 总是（垃圾风险） |
| unexpected_reward | Noul | …announce an unrequested prize, bonus, or payment? | 意外奖励 | 总是（垃圾风险） |
| mentions_open_order | Noul | …refer to one of `customer.open_orders`? | 提到未完成订单 | 订单泳道 |
| frustration | Score | How frustrated does the customer appear? 3 级情境 | 愤怒度 | 总是（优先级） |

## 代码里的组合规则（`compose.ts`）

按顺序首中：
1. **硬规则**：`requests_credentials ≥ 0.9` → 隔离（不依赖加权和）。
2. `spamRisk = 0.45·索要凭证 + 0.30·身份不符 + 0.25·意外奖励`；`≥ 0.6` → 隔离；`(0.4, 0.6)` → 人工复核。
3. 部门 = other，或部门置信度 `< 0.6` → 人工复核。
4. 否则进入部门泳道；其它部门概率 `≥ 0.25` → 抄送。
5. 优先级 = `0.5·愤怒度/2 + 0.5·（技术泳道 ? 严重度/2 : 0）`；徽章：退款 ≥0.7、可复现 ≥0.6、未完成订单 ≥0.7、愤怒 ≥1.5、阻塞 ≥1.5。

所有数字都在 `thresholds.ts`，也就是页面右侧的滑杆。

### 为什么需要硬规则（实测教训）

第一次冒烟时 T22（"Security Team" 索要一次性验证码）落在灰区而不是隔离：它的发件人没有可识别的组织名，`sender_identity_mismatch` 只有约 0.2，`unexpected_reward` 为 0，于是即使 `requests_credentials` 接近 1，加权和最多 0.45 + 0.06 ≈ 0.50，永远够不到 0.6。加权和适合"互相补偿"的偏好；**"任何一条严重违规就拦"必须是单独条件**——这与官方文档的建议一致。加入硬规则后 24/24 命中。

## 试一试

1. 把"部门置信度门限"拉到 1.00：T06、T20、T24 等置信度略低于 1 的工单立刻进入人工复核；计数器显示"0 次新推理"。
2. 把"硬规则"门限拉到 1.00，再把"索要凭证"权重调到 0：T22 会回到灰区甚至账户泳道——这就是只靠加权和的漏洞。
3. 把"垃圾风险隔离线"降到 0.4：观察是否有正常工单被误隔离（应该没有：正常工单的风险都 ≤ 0.04）。
4. 点开 T23，勾选"显示被忽略的 speculative 答案"，看 bug_severity 等与该工单无关的答案长什么样。

## 陷阱

- 阈值只是起点：真正的门限要用你自己的工单与后果来定，并定期复核。
- Noul 上调好的阈值不能搬到 Choice；`P(索要凭证)` 与 `1 − P(不索要凭证)` 不一定相等。
- 加权和是策略，不是模型；严重违规要单独设条件。
- 10 题一次请求的成本随工单数线性增长；省钱的是"重排不重推"。
