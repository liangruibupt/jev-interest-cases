# 05 · 成本模型：Jev 带来的成本下降预估

## 方法

应用里每个场景的"成本对比"卡按以下方法估算"如果用 LLM 做同样的判断"要花多少：

1. **输入 tokens** = 真实发给 Jev 的 `input_tokens`（同样的 state + 同样的问题，LLM 也得读一遍）。
2. **输出 tokens** = 每场景一个假设常量（LLM 必须生成 JSON/答案；Jev 输出免费），见下表。
3. 按所选 Claude 层级的公开价计算；Jev 按 $0.042/Mtok 输入计算（缓存命中也按 tokens 计，保证对比公平）。
4. 假设全部展示在卡片里，可切换基线模型。A4 与 B1 另有**实测**数字。

价格（$/Mtok 输入 / 输出）：Jev 0.042 / 0；Sonnet 5 2 / 10；Opus 5 5 / 25；Sonnet 4.6 3 / 15；Fable 5.1 10 / 50。

## 结论与适用条件

- **判断 / 分类 / 核验 / 筛选步骤本身**：下降约两个数量级。预估 50–340×；**实测 50×（A3）到 635×（A4，对比 Opus 5）**，8 个场景全部落在这个区间，与官方 cookbook 的 76×–900× 同量级。倍数主要由"每次判断要读多少上下文"决定：A3 一次读 12k tokens 只有 50×，A4 一次读 1.1k 达到 250–635×。
- **含生成的端到端流程**：预估 30–65%；**实测 29%（B2）、47%（B3）、85%（B4）、87%（B1）**。生成仍然需要 LLM；Jev 的价值是让生成只发生在必要的地方（B1 一半消息零生成、B4 八成指令零生成）、只吃必要的上下文（B3 prompt 缩短 6 倍）。
- **不占优的情况**：相对向量检索（A3），Jev 每次查询贵约三个数量级；相对纯确定性代码，Jev 永远不如 `if`（B2 的字符串匹配、B4 的正则都先于 Jev）。
- **延迟**：本网络实测 Jev p50 0.35–0.8 s（官方约 100 ms），Claude Sonnet 5 经 Bedrock 2.7–10 s；判断步骤快 5–15 倍。
