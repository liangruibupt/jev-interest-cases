# 05 · 成本模型：Jev 带来的成本下降预估

## 方法

应用里每个场景的"成本对比"卡按以下方法估算"如果用 LLM 做同样的判断"要花多少：

1. **输入 tokens** = 真实发给 Jev 的 `input_tokens`（同样的 state + 同样的问题，LLM 也得读一遍）。
2. **输出 tokens** = 每场景一个假设常量（LLM 必须生成 JSON/答案；Jev 输出免费），见下表。
3. 按所选 Claude 层级的公开价计算；Jev 按 $0.042/Mtok 输入计算（缓存命中也按 tokens 计，保证对比公平）。
4. 假设全部展示在卡片里，可切换基线模型。A4 与 B1 另有**实测**数字。

价格（$/Mtok 输入 / 输出）：Jev 0.042 / 0；Sonnet 5 2 / 10；Opus 5 5 / 25；Sonnet 4.6 3 / 15；Fable 5.1 10 / 50。

| A2 每条工单 | LLM 一次 JSON 分类 10 字段 | 700 in / 250 out | $0.00003 | Sonnet 5 $0.0039 · Opus 5 $0.0098 | **≈99.2%（130×）– 99.7%（330×）**，改阈值另省 100% 重跑 |
| A3 每次查询 | LLM 读全文指出行号 | 11k in / 100 out | $0.00046 | Sonnet 5 $0.023 · Opus 5 $0.058 | **≈98%（50×）– 99.2%（125×）**；对比向量检索**不省钱**，优势是零索引与可解释 |

| B4 混合流量 20 条 | 全走 LLM function calling | 20% 需拆分/闲聊各加一次 Sonnet 5 | $0.011 | Sonnet 5 $0.064 · Opus 5 $0.16 | **≈83%（6×）– 93%（15×）**；延迟 0.1s vs 1–3s |

## 结论与适用条件

- **判断 / 分类 / 核验 / 筛选步骤本身**：下降约两个数量级（50–340×），与官方 cookbook 的 76×–900× 同量级。
- **含生成的端到端流程**：下降 30–65%。生成仍然需要 LLM；Jev 的价值是让生成只发生在必要的地方、只吃必要的上下文。
- **不占优的情况**：相对向量检索（A3），Jev 每次查询更贵；相对纯确定性代码，Jev 永远不如 `if`。
